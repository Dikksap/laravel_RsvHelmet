The module centers on `app/Services/ExternalBarangSyncService`, which orchestrates three sync flows: (1) `sync()` — paginated per-unit pull with idempotency keyed by `kode_barang` against `external_synced_barangs.inventory_movement_id`; (2) `syncVariantOutput()` — aggregates all eligible units of one external variant into a single stock-in movement; (3) `syncBatchOutput()` — groups units by mapped RSV item for a given external batch code and emits one movement per item. It delegates HTTP calls to `ExternalBarangApiService` and persistence to `StockMovementService::record()`. The Filament page `DaftarBarangEksternal` exposes the batch-based modal (production batch, external batch code, status, warehouse, optional max_units) plus a variant-mapping action that writes `ExternalItemMapping`. A CLI command `SyncExternalBarangCommand` mirrors the same service options (`--warehouse`, `--batch`, `--kode-batch`, `--limit`, `--all-pages`, `--status`, `--dry-run`). Idempotency is enforced via the `external_synced_barangs` table whose migration defines `inventory_movement_id` as nullable with `nullOnDelete`, so deleting a movement leaves an orphaned row that currently still blocks re-pull through the `whereNotNull('inventory_movement_id')` check in both `sync()` and `collectUnits()`.
